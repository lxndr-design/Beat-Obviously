Beat Plugin Help

Beat currently supports plugin-style instruments through safe import adapters. The supported path is DecentSampler package import plus a Beat sampler bridge. AU/VST3 live hosting is not enabled yet.

Updated 2026-07-04.

DecentSampler

DecentSampler support is an import adapter, not a live plugin host. Beat reads the package, registers its samples, preserves UI metadata, and creates a Beat sampler-backed instrument that can be placed on tracks.

  • Supported files: `.zip`, `.dspreset`, `.dslibrary`, `.dsconfig`, and compatible XML preset files.
  • Sample zones keep key/velocity ranges and start/end offsets when present.
  • Package UI skin metadata is preserved for the DS package wrapper.
  • Dragging a DS package into a track creates an instanced instrument linked to that DS package.
  • Right-clicking compatible track segments can open the DS edit action for that instrument/package.

Import Workflow

  1. Open the DS rail tab or plugin import action.
  2. Choose a `.zip` or `.dspreset` file.
  3. Leave editor mode on Auto unless the package needs Drum or MIDI forced manually.
  4. Install from the native app so Beat can read files and register sample assets.
  5. Drag the installed DS package or created instanced instrument onto a track.
  6. Save the project so the plugin adapter, associated instrument id, and copied assets are persisted.
Browser preview can show lightweight package shells, but native app import is required for full ZIP extraction and reliable sample registration.

Adapter Model

A Beat plugin adapter is serializable project data that describes what a plugin-style package can do. The current TypeScript shape is represented by PluginAdapter.

FieldPurpose
kindsynth, effect, renderer, or utility.
formatnative, vst3, audio-unit, bridge, or decent-sampler.
statusavailable, installed, missing, or blocked.
instrumentModelive-instrument, rendered-audio, or fallback-aether.
associatedInstrumentIdLinks an adapter to the Beat instrument that actually plays in tracks.
capabilitiesLists instrument/effect/render/utility capability, realtime/offline support, latency, and fallback mode.

How To Make A Plugin Adapter

Until Beat has a public plugin SDK, a "plugin" should be built as a safe adapter around serializable project data, not as arbitrary code running in the audio callback.

  1. Choose the adapter format: usually native for internal Beat adapters or decent-sampler for DS packages.
  2. Define import data that can be saved in a `.beat` project without needing the original download folder.
  3. Register all audio assets with Beat's audio-file library or package sidecar.
  4. Create or link an associated Beat instrument if the adapter plays notes.
  5. Declare capabilities: instrument/effect/renderer/utility, realtime/offline support, latency, and fallback behavior.
  6. Add project-health validation for missing files, missing associated instruments, stale references, and unsupported runtime modes.
  7. Add a verifier or backend stress fixture that proves import, save/open, live playback, and export behavior.

Minimum Internal Checklist

  • Parser rejects unsafe paths and malformed packages.
  • Import copies or registers assets into Beat-managed storage.
  • Adapter state is serializable and document-roundtrip safe.
  • Project Health reports missing or broken dependencies.
  • Live playback and export agree, or the difference is documented.
  • The UI opens an adapter-specific editor instead of falling back to Aether unless explicitly intended.

Project Files

Plugin adapters are stored alongside project instruments and audio references. DecentSampler adapters also store the associated Beat sampler instrument id so reopened projects do not silently change sound engines.

Safety Rules

  • ZIP entries must not be absolute paths.
  • ZIP entries must not contain drive prefixes or `.` / `..` segments.
  • Imported package data should live in Beat-managed storage, not the Downloads folder.
  • Unavailable plugin processors must be pass-through or blocked, never crash the audio callback.
  • Native binary plugin hosting must be isolated before it is allowed in a realtime path.

Future Hosting

AU/VST3 support should be a dedicated protected-host project: scanning, validation, crash isolation, UI hosting, latency reporting, preset persistence, offline render, and project-health recovery must land together. The current placeholder metadata exists so projects can preserve intent without pretending the host is already safe.
