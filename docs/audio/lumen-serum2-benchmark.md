# Lumen / Serum 2 Benchmark

## Boundary

Lumen is Beat's Aether-successor synth, not an Aether rename or in-place schema upgrade. For compatibility, existing projects and APIs continue to persist its historical instrument type `lumen-hybrid-synth` and namespace `lumen`; only the user-facing product name changes. Aether remains frozen under instrument type `wavetable-synth` and namespace `synth`. Lumen has a separate creation path and engine identity. Its first audible foundation deliberately adapts into the verified Aether renderer so the starting sound is deterministic; future Lumen features must extend this boundary without changing Aether patches or defaults.

No Serum 2 plug-in is installed on the measured machine, so no direct sound-quality, null-test, CPU, preset, or render claim is made against Serum 2. The current comparison is a feature-contract benchmark derived only from Xfer Records' official [product page](https://www.xferrecords.com/products/serum-2), [sound-generation overview](https://xferrecords.com/web-manual/serum-2/exploring-sound-design-in-serum), [routing documentation](https://xferrecords.com/web-manual/serum-2/routing-an-oscillator-or-filter), [architecture overview](https://xferrecords.com/web-manual/serum-2/exploring-serum), and [version-compatibility FAQ](https://support.xferrecords.com/article/58-how-to-upgrade-from-serum-1-to-serum-2). These sources are behavior references only; no third-party code, preset, wavetable, sample, artwork, branding, or service integration is used.

The machine-readable matrix is `docs/audio/lumen-serum2-capability-matrix.json`.

## Initial measured baseline

Lumen Init currently uses the same parameter values and renderer adapter as Aether Init. Focused frontend coverage requires its 48 kHz stereo float buffers to be byte-identical to Aether Init while preserving the distinct legacy Lumen type and namespace through normalization, instrument conversion, and restoration. Native contract coverage requires the same patch to select `InstrumentDefinition::SynthEngine::Lumen`; an Aether patch must continue selecting `SynthEngine::Aether`.

This equality is a starting-line invariant, not a permanent goal. Every future divergence must name the Lumen-only contract, add a measured render, and prove the equivalent Aether render remains unchanged.

### Equivalent-patch performance gate — 2026-07-26

`scripts/benchmark-lumen-aether-equivalence.mjs` closes the Beat-internal foundation gate without changing either renderer. It starts from the two frozen Beat-authored Aether benchmark instruments, constructs each Lumen counterpart through the production `cloneAetherDraftAsLumen` path, keeps the identity-seeded patch name constant, and leaves Source C, Arp, and Clip disabled. The matrix covers 44.1/48/96 kHz, 128/512-sample blocks, and 1/4/8 submitted voices. Every case records stereo SHA-256 values, maximum sample delta, callback-sized render calls, voice-sample frames, source-dispatch checks, active oscillator-lane frames, five alternating-order wall measurements, and the median Lumen/Aether wall ratio.

The pass budget is exact output (`maxSampleDelta = 0`), exact active oscillator-lane work, no row above a `1.15` median wall ratio, and an aggregate ratio no higher than `1.10`. The verified run produced eight of eight byte-identical Aether/Lumen rows, zero active oscillator-lane-frame delta, a `1.083382` aggregate ratio, and a `1.089869` slowest row. Lumen carries one additional configured but disabled Source C, so the telemetry intentionally shows three inexpensive source-dispatch checks per voice/sample versus Aether's two; it does not mislabel those checks as active oscillator DSP. This bounded control-path cost is the documented reason the wall result is not exactly 1.0.

This is a frontend offline-render wall/work benchmark, not CPU-instruction telemetry or a native callback deadline measurement. The JSON snapshot is written to `beat-lumen-aether-equivalence/lumen-aether-equivalence.json` under the selected output directory. The existing frozen Aether render verifier remains independent and its hashes are not updated. No Serum 2 renderer participates, so this closes only the internal Aether/Lumen equivalent-patch gate and makes no Serum 2 parity claim.

`build-native/bin/BeatBackendStress --lumen-v2` is the corresponding focused native lane. This establishes Lumen as a V2 release candidate, not a completed V2 release. ## Three-slot source rack

Lumen schema v15 retains three stable source identities: A, B, and C, and gives each slot independent sample and granular parameters, managed assets, and Wavetable/Sample/Multisample/Granular selection. Sample mode adds bounded Forward/Reverse direction, 0.25x-4x playback rate, Forward/Ping-pong loop traversal, a 1-2000 ms note-off release tail, and up to 16 manually authored stable-ID slices independently to A, B, and C. A selected slice replaces the effective playback region while preserving the base Full Region; reverse, loop bounds, ping-pong, and the release tail remain constrained to it. Decoded samples, bounded mapped zones, and managed SFZ regions use the same selected-region policy. V11 records migrate to neutral Forward/1x values; v12 records retain those transforms while receiving Forward loops and the established 4 ms anti-click tail; v13 records migrate to empty, unselected slice lists; v14 records retain their established sound and normalize unsupported future spectral names to Shape. Multisample deliberately retains its neutral mapping policy. Ping-pong reflects decoded/mapped voices at valid loop bounds; managed SFZ regions opt in through their existing continuous or sustain loop declarations. Multisample is an explicit policy identity over the same bounded key-map/SFZ renderer rather than a duplicate DSP engine. The generalized oscillator editor presents exactly those rows and disables structural add/remove actions. Non-wavetable modes disable only the selected slot's wavetable renderer. V3 sample data migrates losslessly into C; v4 gains silent granular defaults while retaining its legacy auxiliary granular state, and v1/v2 remain wavetable-only and silent for C.

Wavetable, sample, multisample, and bounded granular modes are implemented independently for A, B, and C. A shared A/B/C settings switch exposes each source asset and key map without creating a second component system. Sample and Multisample deliberately share the verified renderer while retaining distinct serialized mode identity. Wavetable mode now offers five Lumen-only prepared harmonic-domain warps, while the separate Serum-style time/frequency spectral source remains paused rather than exposed as a placeholder. Slot C wavetable mode participates in the existing modulation contract. All source-mode and routing UI uses Beat's shared `FloatingSelect`, button, toggle, input, and knob components with no Lumen-specific typography or layout system.

Schema v7 added a Lumen-owned arpeggiator. Schema v8 added zero-to-75% pair-preserving swing. Schema v9 adds twelve root keys and Chromatic, Major, Natural Minor, Major Pentatonic, and Blues contexts. Incoming held notes are quantized to the nearest allowed pitch before pattern ordering; exact ties resolve downward, then the existing octave expansion applies. Chromatic is the default, and v1-v8 migrate to C Chromatic, preserving older output. When enabled, the route-level MIDI transform produces Up, Down, Up/Down, or deterministic Random patterns at 1/4, 1/8, 1/16, or 1/32 divisions, with bounded gate, swing, and octave controls.

Schema v11 upgrades the mutually exclusive clip sequencer to one bounded polyphonic clip. A clip contains 1-32 steps and up to 64 relative notes with integer start, pitch offset, whole-step length, and velocity. Multiple notes may share a start step to form chords. The most recently held input note triggers and transposes the pattern; releasing it deterministically falls back to the most recently pressed note still held. New triggers restart at step one. Active notes receive independent note-offs, and a same-pitch/channel retrigger retires the older active entry before starting the replacement. The clip supports the same four tempo divisions and pair-preserving swing range. Clip and Arpeggiator cannot both be active. V10 schema-1 step clips migrate one-way into schema-2 note lists, older patches receive an empty disabled 16-step clip, and malformed/future/conflicting data is rejected before preparation. The Lumen editor reuses Beat's existing piano roll through a pure relative-note adapter and can import instrument-independent MIDI patterns while preserving relative pitches, timing, lengths, and velocities. Clip banks, live clip recording, macro automation, and preset-preview designation remain explicit gaps.

Both transforms recalculate step duration from the active sample rate, sequencer tempo, and transport speed. Held-note state, order, channel, velocity, block continuity, note-offs, and controller panic behavior are deterministic; transport reset clears the active transform. The callback uses fixed arrays and a pre-sized MIDI buffer, while validation, configuration, and storage preparation happen outside it.

The MVP routing contract freezes two fixed pre-insert source sends plus a stored-order main insert chain. Each source independently selects Shared Filter, Filter 1, Filter 2, Direct, or None; missing return targets are silent rather than rerouted. Instrument inserts precede track inserts, and return buses own their downstream effect chains. Native save/reopen now preserves Lumen engine identity and the complete bounded Lumen configuration rather than reconstructing the record as the shared Aether adapter. A focused lifecycle fixture proves Slot C routing/tuning, clip state, bus targets, insert order/bypass, return effects, and sample-identical post-reopen output.

The focused MIDI transform is event-exact across 100-sample block splits and reports zero realtime-safety violations after preparation. The end-to-end offline engine test produces finite, audible, materially different enabled output (`differenceEnergy 647.748`) and a `0.003130` maximum sample delta between 64- and 257-sample render blocks, below the explicit `0.005` integration tolerance. The disabled comparison is block-identical. This tolerance records the renderer's retrigger/envelope numerical boundary rather than relaxing MIDI event timing.

The v16 capability bank adds seven Beat-authored archetypes: `Lumen_SubBass_02`, `Lumen_ArpPluck_02`, `Lumen_WidePad_02`, `Lumen_MonoLead_02`, `Lumen_DigitalKeys_02`, `Lumen_ClipSequence_02`, and `Lumen_GranularTexture_02`. Together they exercise three-source tuning/routing, prepared Spectral Smear/Harmonic Shift/Spectral Skew modes, mono and polyphonic lifecycle behavior, keytracked LFO motion, arpeggiator and clip transforms, dual filters, ordered inserts, ratio tuning, and Slot C granular mode. Automated auditions require finite output, useful level below full scale, stable Lumen identity/roundtrip, material pairwise render differences, and in-place migration from the earlier bank. The hands-on cases are recorded in `docs/audio/lumen-mvp-test-bank.md`.

## Benchmark lanes

1. **Identity and compatibility:** distinct stable type, namespace, editor entry, persistence, and explicit one-way Aether conversion only.
2. **Source architecture:** three interchangeable main slots, each capable of the approved Lumen source modes, plus dedicated sub/noise.
3. **Audio quality:** pitch, alias-risk, DC, discontinuity, cross-rate equivalence, stereo coherence, transition continuity, and deterministic live/offline parity.
4. **Routing and modulation:** per-source dual-filter/main/direct/none routing, two sends, bounded effect graph, deterministic modulation, and unchanged event timing.
5. **Performance:** equivalent cloned Aether/Lumen patches must remain sample-exact, retain equal active oscillator work, stay within the 1.10 aggregate / 1.15 per-row frontend wall budget, and preserve the separately frozen Aether hashes. New modes receive independent realtime work budgets and offline-HQ measurements.
6. **Workflow:** the synth-owned arpeggiator, pair-preserving swing, key/scale context, and bounded single-clip polyphonic piano-roll workflow are complete; clip banks, recording/import, and macro automation remain independently gated work.

## Current conclusion

Lumen has a clean identity boundary, a bit-stable Aether-derived starting renderer, an explicit source-preserving Aether clone path, a fixed A/B/C rack with independently verified sample, multisample, and granular playback in every slot, five prepared harmonic-domain wavetable warps, bounded manual Sample slicing, a bounded sample-accurate arpeggiator, and a deterministic single-clip polyphonic workflow. Automatic transient slicing/snap, clip banks, recording/import, macro automation, preset-preview designation, and a full time/frequency spectral source remain incomplete and are not implied ready by this benchmark.

### Parity refresh — 2026-07-26

The historical lineage remains unchanged: Aether is the frozen Serum 1-style wavetable foundation, while Lumen is the separately versioned Aether 2 / Serum 2-style successor. The expanded matrix now distinguishes source-mode breadth from depth. Lumen meets the three-slot, wavetable-creation, prepared harmonic-warp, multisample/SFZ, bounded Sample direction/rate/ping-pong/release-tail/manual-slice, source-routing, dual-filter, effects-bus, modulation, explicit Aether-conversion, and internal equivalent-patch performance foundations. The clone is one-way and opt-in: it creates a derived Lumen instrument, retains the Aether original and lineage, preserves the existing musical state, and leaves every Lumen-only sound/performance extension silent. Its largest Serum 2 gaps are a full time/frequency and transient-aware spectral source; automatic transient slicing/snap, snap-loop, tape-stop, score-extraction, and specialized tails behavior; full granular breadth; custom source/aux modulation curves and visualization; and clip banks/recording/import/macro lanes.

The next implementation order is therefore:

1. Extend the now-integrated reusable MIDI-pattern import with clip banks and live recording before adding more sequencing surfaces.
2. Continue snap-loop detection, automatic transient slice creation/snap, score extraction, tape-stop automation, and specialized tails modes through the existing bounded per-slot asset contract.
3. Extend the v15 prepared harmonic-warp foundation with dedicated alias, transition, CPU, persistence, and live/export metrics before deciding whether to build the separate spectral source mode.
